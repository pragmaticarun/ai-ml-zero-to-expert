Block 1: Concept lesson (1h15)

Evaluate on several axes. A fine-tune is a trade. Measure: 1. The target task, with an exact metric where possible (exact match, unit tests, F1). 2. Retention: perplexity or tasks from the original domain, to detect forgetting. 3. General ability: standard benchmarks.

Perplexity is cheap and sensitive but only comparable with the same tokenizer and text, and it does not measure helpfulness.

Multiple-choice benchmarks (MMLU, HellaSwag, ARC and others) are often scored by log-likelihood: compute log P(option | question) for each option and pick the highest. Choices matter: summing token log-probs penalises long options; length normalisation (mean per token) or per-character normalisation counteracts that. Different harnesses make different choices, so the same model can get different scores. Always report how it was scored.

Generative evaluation checks free-form answers by exact match, by execution (code), or by a judge.

LLM-as-a-judge (Zheng et al., 2023, "Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena") uses a strong model to grade or compare answers. It scales, but it has known biases: position bias (preferring the first or second answer), verbosity bias, and self-preference. Mitigation: evaluate both orders and count only consistent verdicts, use rubrics, and check agreement with humans on a sample.

Contamination. Benchmark questions leak into web-scale pretraining data, which inflates scores. Prefer held-out or freshly written tests for decisions that matter.

Block 2: Worked example (45 min)

Run code/week-15/day104_eval_finetuned.py (35 s; needs the Day 103 adapter). Models: base, SmolLM2-135M-Instruct, and base + the Day 103 SFT adapter (loaded with 0 unexpected keys). Verified:

base instruct base + SFT LoRA
reverse-words exact match (40) 0.00 0.00 1.00
Shakespeare val perplexity 26.29 32.05 57.90
16-question MC, sum log-prob 0.88 0.88 0.88
16-question MC, length-normalised 0.81 0.81 0.81
  • Forgetting is real: the SFT adapter more than doubled Shakespeare perplexity (26.29 → 57.90) while learning the task perfectly. The instruct model is also worse than the base at plain text continuation (32.05), a common side-effect of chat post-training.
  • The small MC set did not separate the models. All three got the same scores. With 16 questions, one question is 6 percentage points, so this set is too small to detect anything but huge differences. Length normalisation lowered accuracy here (0.81 vs 0.88), so it is not automatically better. The questions were written for this course (basic facts, 4 options), not taken from a benchmark.
  • Position bias, demonstrated. Using the instruct model as a judge ("Which statement is true? A … B …"), on 16 pairs in both orders: it chose A in 10 of 32 cases, gave the same verdict after swapping in 0 of 16 pairs (always the same letter regardless of content), and was correct 16 of 32 times, exactly chance. A 135M model is far too weak to judge, and this is the failure mode the swap test exists to catch.

Block 4: Practice problems (1h)

  1. Standard error of accuracy 0.88 on 16 questions? Answer: sqrt(0.88·0.12/16) ≈ 0.081.
  2. What does a judge consistency of 0/16 mean? Answer: its verdicts depend only on position.
  3. Why might length normalisation hurt? Answer: it can favour long options whose later tokens are easy to predict.
  4. Name two ways to reduce the forgetting seen here. Answer: mix general text into SFT data; lower lr / fewer steps / smaller rank; keep adapters separate and switch them off when not needed.

Block 5: Review (1h)

Extra notes: evaluation harnesses

EleutherAI's lm-evaluation-harness and Hugging Face's lighteval implement many benchmarks with fixed prompts and scoring rules, which makes numbers comparable within a harness. When a model card reports a benchmark, look for the harness, the number of shots, and the normalisation.

Going deeper (optional)

Read Zheng et al. (2023), section 3 on judge biases.

Interview-style question (15 min, written)

"How would you evaluate a fine-tuned support chatbot?" Task metric on held-out real tickets, retention checks, safety tests, judge with swap test and human spot checks, and online A/B metrics.

Common mistakes / how to debug

  • Reporting one tiny test set without error bars.
  • Using an LLM judge without checking position bias.
  • Comparing perplexities across tokenizers.
