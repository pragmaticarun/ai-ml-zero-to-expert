Block 1: Concept lesson (1h15)

Project question. With the same data and number of steps, how do full fine-tuning and LoRA variants compare in target quality, trainable parameters, time and forgetting?

Design. One script (day105_project_lora.py), one seed, Shakespeare as the target domain, and this course's own notes (weeks/week-01.md, 12,705 SmolLM tokens) as the forgetting probe: modern technical English, very different from Shakespeare. Same 80 steps of 4 × 128 tokens for every run. Full fine-tuning at lr 5e-5 (Day 100); LoRA at lr 1e-3 (Day 101).

Confounders to keep in mind. The learning rates differ (each is a typical value for its method), and there is one seed. So the comparison is "typical settings", not "equal settings". A fair study would tune the learning rate per method and average seeds.

Deliverables. The results table, a 300-word report with a recommendation, and Quiz 15.

Block 2: Worked example (45 min)

Run code/week-15/day105_project_lora.py (250 s total). Verified:

run trainable Shakespeare val ppl notes ppl time (80 steps)
no training 0 26.29 24.89 —
full fine-tune, lr 5e-5 134,515,008 21.34 26.29 59 s
LoRA q,v r = 2 115,200 23.23 27.11 48 s
LoRA q,v r = 8 460,800 23.02 28.29 35 s
LoRA q,v r = 32 1,843,200 22.68 30.17 38 s
LoRA all-linear r = 8 2,442,240 21.42 28.65 51 s

Findings: - Target quality: full fine-tuning was best (21.34), with LoRA on all linear layers nearly equal (21.42) using 1.8% of the trainable parameters. On q,v only, higher rank helped modestly (23.23 → 22.68 from r = 2 to 32). Where you adapt mattered more than rank: all-linear r = 8 beat q,v r = 32 with a similar parameter count. - Forgetting: every run got worse on the course notes. Here full fine-tuning forgot least (24.89 → 26.29), and LoRA forgetting grew with rank (27.11 → 30.17). That is the opposite of the common intuition that LoRA forgets less; Biderman et al. (2024), "LoRA Learns Less and Forgets Less", report that pattern at much larger scale. The likely cause here is the learning rate: LoRA ran at 1e-3, 20× higher than full fine-tuning. This is why the confounder note above matters. - Time: LoRA steps were faster (35-51 s vs 59 s) but not dramatically, because the forward and backward passes through the frozen model still dominate on CPU. Timings varied between runs (r = 2 took longer than r = 8), so do not over-read them.

Block 4: Practice problems (1h)

  1. Which run gives the best target ppl per trainable parameter? Answer: LoRA q,v r = 2 (23.23 with 115,200).
  2. Why didn't LoRA give a big speed-up? Answer: compute is dominated by passes through the frozen 134.5M-parameter network; LoRA mainly saves optimiser memory.
  3. What single change would most improve the fairness of the comparison? Answer: tuning the learning rate per method.
  4. When would you still choose LoRA even if full fine-tuning is slightly better? Answer: limited memory, many tasks on one base, small adapter files.

Extra notes

This week's whole arc ran on a CPU with a 135M-parameter model in minutes per experiment. The same scripts work unchanged on a GPU with a larger model (for example a 1-2B parameter model) by moving tensors to cuda and using bf16, at which point real 4-bit QLoRA via bitsandbytes becomes available and runs of thousands of steps are practical.

Going deeper (optional)

Read Biderman et al. (2024) and compare their learning-rate choices with ours.

Interview-style question (15 min, written)

"Full fine-tuning or LoRA for a new product?" Start with LoRA on all linear layers (cheap, swappable), measure target and retention, and escalate to full fine-tuning only if the target gap matters and you can afford it.

Common mistakes / how to debug

  • Comparing methods at different learning rates and attributing the difference to the method.
  • No retention probe.
  • One seed reported as a conclusion.
