Block 1: Concept lesson (1h15)

The project joins the week's pieces into one small service that a reviewer could actually operate: 1. Traceable artefacts. An ONNX model plus meta.json, which records the model weight hash, data-version hash (Day 142), threshold (Day 141's cost choice), feature names, drift reference and calibrated drift threshold, and golden predictions. 2. A strict interface. Wrong shapes, NaNs, wrong types and oversized batches get HTTP 422, fixing the Day 144 flaw where a bad shape returned 200. 3. Tests as a release gate: health, golden-prediction parity, an accuracy floor, bad inputs, a batch limit, and a drift alarm that must stay quiet on clean data and fire on drifted data. 4. Monitoring built in. /metrics reports request, row and rejection counts, model-only p95 latency, and drift (max PSI over a rolling 500-input window, which feature, and whether it alerts). 5. A calibrated drift threshold. Day 145 showed PSI > 0.2 alarms on 48/50 clean batches. Instead, take the 99th percentile of max-PSI over no-drift windows. 6. A load test against an SLO (p95 < 50 ms on this box). 7. A model card generated from the same run, so its numbers cannot drift from reality. 8. Container and CI files, clearly labelled UNTESTED.

Model cards (from Mitchell et al.'s proposal; written here in my own structure) document what a model is, the data it used, intended and out-of-scope uses, metrics with uncertainty and by slice, how it is monitored, and known limits. Writing the card from the run rather than by hand keeps it honest.

Block 2: Code walk-through (1h)

day147_project.py: - trains the Day 143 tied-best default config (h=32, lr=1e-2, seed 0), exports it to ONNX, and writes project/artifacts/; - calibrates the drift threshold on 200 no-drift windows of 143 rows resampled from the training data; - runs pytest on project/test_service.py; - starts project/service.py under uvicorn, runs a 500-request load test at concurrency 8, and sends clean traffic then area ×1.3 traffic, reading /metrics after each; - writes project/MODEL_CARD.md.

Two bugs found and fixed while building it: - An exec of the service file inside the build script overwrote its artefact path, causing FileNotFoundError on meta.json. I removed the exec. - A test sending float("nan") crashed inside the test client, because strict JSON cannot encode NaN. Python's JSON parser does accept the literal NaN, though, so a real client can send it. The test now posts the raw text NaN and checks for a 422.

Verified (out/day147_project.log): - Data version 9f2384ac7409; model 53df326a18b85c38; test accuracy 0.965; threshold 0.8. At 0.8: missed malignant 2, false alarms 4; accuracy by mean-area tertile small 1.000, medium 0.915, large 0.958. Day 141's large-tertile 0.979 was at threshold 0.5; the higher threshold trades accuracy for fewer misses. - Calibrated drift threshold: 0.234 (99th percentile of max-PSI over 30 features), vs the 0.2 rule of thumb. - pytest: 10 passed. - Load test, 500 single-row requests at concurrency 8: p50 7.8 ms, p95 21.7 ms, 769 req/s. SLO p95 < 50 ms met. Model-only p95 about 0.17 ms, so roughly 99% of request time is not the model. - /metrics after 500 clean rows: max PSI 0.187 ("worst symmetry"), alert false, rejected 0. - /metrics after 500 rows with area ×1.3: max PSI 0.658 ("mean area"), alert true. It names the right feature.

Honest limits: - The threshold was calibrated on 143-row windows while the service uses 500-row windows. Larger windows have less sampling noise, so the threshold is conservative there (fewer false alarms, slower detection). - Labels are not observed, so the service cannot see accuracy loss or concept drift. - One seed; 143 test rows, where one error is 0.007. - Docker and CI are untested, and the load test ran client and server on one machine.

Block 3: Exercises (1h30)

  1. Recalibrate the drift threshold with 500-row windows to match the service, and re-run the quiet and loud tests.
  2. Add a /feedback endpoint that accepts delayed labels and reports rolling accuracy. Then inject concept drift and watch it.
  3. Add a shadow model (Day 143's h=128 config) that scores every request without affecting the response. Log disagreement rate and latency.
  4. Make the CI workflow fail if MODEL_CARD.md changes without a version bump.

Block 4: Self-check (30 min)

  1. Why generate the model card from the run? So every number in it is the measured one, and it cannot go stale.
  2. What do golden-prediction tests catch? Export, preprocessing or dependency changes that alter outputs.
  3. Why calibrate the PSI threshold? A fixed 0.2 gave 48/50 false alarms with 30 features. Calibration gives 0.234 at a 1% false-alarm target per window.
  4. Did the drift alert identify the cause? Yes. Max PSI 0.658 on "mean area" after area ×1.3.
  5. What can this service still not detect? Concept drift and accuracy loss, without labels.

Block 5: Reflection (15 min)

If you were on call for this service, which single /metrics field would you page on, and which would you only chart?

Extra notes. Real services add authentication, rate limiting, structured logs, tracing, multiple replicas and a registry-driven deploy. Each is a layer on the same skeleton.

Going deeper. Build the Dockerfile on a machine that has Docker, fix whatever breaks, and record what you changed. Until then it stays labelled UNTESTED.

Interview-style question (15 min). "Walk me through what happens when this model is retrained." New data is validated and versioned. Training is tracked and reproducible, with selection by mean over seeds. CI exports, checks parity and runs golden, floor and input tests. A new card is generated. Then shadow, canary with rollback, and promotion, with the drift reference updated to the new training data.

Common mistakes. Hand-written model cards. Thresholds copied from blog posts. Returning 200 on errors. Tests that only run on the happy path. Calling localhost load tests production numbers.
