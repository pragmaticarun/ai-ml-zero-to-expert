Interactive weekly quiz (12 questions)

Q1.

What does mean pooling do in a sentence-embedding model, and why normalise the result?

It averages token vectors (masked) into one vector; normalising makes dot product equal cosine similarity.

Q2.

In Day 113, which chunking gave the best recall@5, and what was it?

Section chunking: recall@5 0.71 (vs 0.62-0.64 for word windows).

Q3.

What is reciprocal rank fusion and why is it convenient?

Score = Σ 1/(k + rank) over retrievers; it uses only ranks, so no score calibration is needed.

Q4.

Why is a cross-encoder more accurate than a bi-encoder, and why is it used only for reranking?

It attends across query and document jointly; it needs one forward per pair, so it is too slow for whole-corpus search (about 200 ms for 20 pairs here).

Q5.

In Day 114, what did reranking the dense top 20 do to recall@1?

Raised it from 0.40 to 0.50 (recall@5 0.64 → 0.81).

Q6.

In Day 115, context recall@3 was 0.92 but accuracy 0.25. What does that tell you?

Retrieval mostly worked; the 135M generator failed to use the context: the main error is generation.

Q7.

Write the symmetric quantisation formula for b bits.

s = max|w| / (2^(b−1) − 1), q = clamp(round(w/s), −2^(b−1), 2^(b−1) − 1), ŵ = s·q.

Q8.

Why did int4 per-tensor destroy SmolLM2-135M while int4 group-64 did not?

Outliers (e.g. max 2.875 vs mean 0.1441 in one layer) set a huge single scale so most weights rounded to zero (ppl 1,561,367.93); group-64 scales adapt locally (ppl 36.89).

Q9.

What is the core idea of GPTQ? Of AWQ?

GPTQ: quantise columns one at a time and update the rest to compensate, using the Hessian XᵀX. AWQ: scale up weight channels that meet large activations before quantising, folding the inverse scale into the input.

Q10.

Why was the Rust int8 kernel slower than torch fp32 at batch 1, and what did it gain?

Torch uses optimised SIMD/blocked BLAS (15.9 µs vs our 145.2 µs with 8 threads); our kernel stored the weights in 4× less memory (884,736 B + 2,304 B scales vs 3,538,944 B).

Q11.

What did the KV cache change in Day 118, and what does it cost?

Decode went from 27.3 to 67.8 tok/s with identical tokens; it costs memory growing linearly with length (94.4 MB at 2,048 tokens per sequence).

Q12.

Why was self-speculative decoding slower than plain decoding here?

The early-exit draft was a poor predictor (acceptance 0.03-0.06), so draft steps were wasted and almost every token still needed a target forward.

  • Combine lexical and dense retrieval, add a cross-encoder reranker, and see what each buys.
  • Build retrieval-augmented generation with a 135M model and separate retrieval errors from generation errors.
  • Implement int8/int4 quantisation from scratch and measure its effect on SmolLM2-135M perplexity.
  • Implement simplified GPTQ and AWQ, and write an int8 matmul kernel in Rust with PyO3.
  • Write a Llama forward pass with your own KV cache; measure cache speed-up, batching throughput and speculative decoding.
  • Weekly project: a RAG system over the notes with fp32, int8 and int4 generators.

Compute note (CPU vs GPU). Everything here fits on a CPU because the models are tiny: the MiniLM embedding model, a MiniLM cross-encoder and SmolLM2-135M. Quantisation is simulated: weights are rounded to int8/int4 and then stored dequantised in fp32, so it measures quality loss but not speed. Real speed-ups need kernels that compute on low-bit weights (on GPUs: GPTQ/AWQ/Marlin-style kernels; on CPUs: llama.cpp's). On a GPU you would also see the KV cache and batching effects much more strongly, and serving engines such as vLLM only make sense there.

llama.cpp on this box: not built. This box has gcc and cc but no g++, no cmake and no make, and llama.cpp is C/C++ built with CMake, so it was not built or run here. Its description below comes only from its README (copy saved as code/week-17/out/docs_llama_cpp_README.md). vLLM is described from its README (out/docs_vllm_README.md); it was not installed (it targets GPUs).
