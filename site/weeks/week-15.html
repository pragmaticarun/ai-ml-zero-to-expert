Interactive weekly quiz (12 questions)

Q1.

Why does SmolLM2's k_proj have 192 output features?

GQA: 3 KV heads × 64 dimensions.

Q2.

What does labels=-100 do?

Excludes that position from the loss.

Q3.

Estimate fp32 AdamW memory for full fine-tuning of 134.5M parameters.

16 bytes per parameter ≈ 2.0 GiB, plus activations.

Q4.

Write the LoRA forward pass and its initialisation.

y = Wx + (α/r)·B A x, with A random and B zero so the model starts unchanged.

Q5.

How many trainable parameters does LoRA r = 8 on q and v add to SmolLM2-135M?

460,800 (15,360 per layer × 30).

Q6.

Why is the merged LoRA output not bitwise identical?

Floating-point rounding (max logit difference 7.4e-05).

Q7.

Name QLoRA's main ingredients.

4-bit NF4 base, double quantisation, LoRA on all linear layers, paged optimisers.

Q8.

What did simulated 4-bit do to base perplexity, and what did LoRA on top achieve?

26.29 → 36.89; LoRA r = 8 all-linear for 60 steps brought it to 25.46.

Q9.

Why did our first instruction-tuning evaluation score only 0.07?

Generation did not stop at <|im_end|>, so correct answers were followed by junk.

Q10.

Did prompt-loss masking matter on our task?

No: both masked and unmasked reached 1.00 exact match.

Q11.

What did the judge swap test show?

0 of 16 verdicts survived swapping; accuracy 16/32, exactly chance: pure position bias.

Q12.

In the project, which run forgot least, and what confounder may explain it?

Full fine-tuning (notes ppl 24.89 → 26.29); LoRA used a 20× higher learning rate.

Week overview, goals, project and quiz text

Status: written in full (Phase 4). Days 102-104 follow the revised plan (peft/QLoRA, instruction tuning, evaluation of the fine-tuned model). SYLLABUS.md now lists these titles; the RLHF overview moved to Day 106 (Week 16). Every number below was printed by a script in code/week-15/ on this box (torch 2.15.0+cpu, transformers 5.21.1, peft 0.21.2, 8 CPU threads, no GPU), with logs in code/week-15/out/*.log. Times were measured with the CPU otherwise idle; on a shared CPU they were up to ~100× slower, so treat them as rough.

Week goals

  • Load, inspect, run and score a real pretrained LM with Hugging Face transformers.
  • Fully fine-tune a 135M-parameter model on CPU and understand its memory cost.
  • Implement LoRA from scratch, verify it against peft, and merge adapters.
  • Understand QLoRA (4-bit frozen base + LoRA) and simulate it on CPU.
  • Instruction-tune a base model with a chat template and prompt-loss masking.
  • Evaluate a fine-tuned model honestly: task metric, forgetting, multiple-choice scoring, judge bias.
  • Weekly project: compare full fine-tuning with LoRA variants on the same budget.

Compute note (CPU vs GPU). A training step of SmolLM2-135M on 4 × 128 tokens took about 0.9 s here (full fine-tune) or 0.5 s (LoRA). That is enough for a hundred steps, which shows the effects, but real fine-tunes run thousands of steps on GPUs with bf16 and larger batches. On a GPU you could also use real 4-bit QLoRA (bitsandbytes kernels are GPU-only; Day 102 simulates the quantisation instead) and models of 1-8B parameters.

Models and data (all downloads verified on this box, cached in data/cache/hf; scripts run with HF_HUB_OFFLINE=1): - HuggingFaceTB/SmolLM2-135M (base) and HuggingFaceTB/SmolLM2-135M-Instruct, Apache-2.0. - Tiny Shakespeare (as Week 14). In SmolLM tokens: 305,111 train, 35,983 val. - Synthetic "reverse the words" instructions generated by day103_instruction_tuning.py (no download).

Shared code: _hf.py (cache path, loading, Shakespeare token batches, windowed perplexity) and _lora.py (LoRA from scratch).

A note on perplexity numbers. _hf.perplexity averages over the first n windows of 256 validation tokens. Day 99 uses 16 windows (24.42); Days 100-105 use 8 windows (26.29 for the same base model). Only compare numbers computed with the same window count.
