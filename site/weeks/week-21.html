Interactive weekly quiz (12 questions)

Q1.

Give the four lifecycle stages and say which one most often changes between iterations.

Scoping, data, modelling, deployment/monitoring. The data usually changes the most.

Q2.

On Day 141, why was threshold 0.8 chosen over 0.5? Give both costs.

Cost = 10 × missed + false alarms: 24 at 0.8 vs 32 at 0.5 (missed 2 vs 3, false alarms 4 vs 2).

Q3.

What did Day 141's learning curve suggest about buying more data?

It was nearly flat after about 25% of the data (0.946 → 0.953), so more of the same data is a poor investment.

Q4.

Which Day 142 fault passed schema validation, and what catches it instead?

Radius +10% passed. Drift detection (PSI/KS) catches distribution shifts.

Q5.

Why did a row-shuffled copy need an order-invariant hash to match?

Raw bytes depend on row order. Sorting rows before hashing makes the hash order-invariant.

Q6.

On Day 143, why is "h=8 seed 0, val 0.972" a bad reason to pick h=8?

It is a maximum over noise. That config's mean over seeds was 0.969; pick by mean.

Q7.

How was reproducibility verified, and did thread count matter here?

By hashing the weights: same seed gave equal hashes (53df326a18b85c38), and fresh processes with 1 and 4 threads gave the same hash. Thread count did not matter here, but that is not guaranteed.

Q8.

Why did onnxruntime's per-call speed-up (4.2× at batch 1) barely show at the HTTP level?

The model is about 5-20 µs of a roughly 1.5 ms request; HTTP, JSON and Python dominate (650 vs 567 req/s).

Q9.

What was the false-alarm rate of PSI > 0.2 over 30 features on clean batches, and of Bonferroni-KS?

PSI: 48/50 batches alarmed. KS with Bonferroni: 2/50.

Q10.

Did any injected drift reduce accuracy on Day 145? What does that imply for alerting?

No. Accuracy stayed at or above 0.945 in every case. Drift alerts should trigger investigation, not be read as degradation.

Q11.

What did peeking 10 times do to the A/A false-positive rate?

It rose from 0.046 (test once) to 0.191.

Q12.

In the project, what drift threshold was used, how was it obtained, and what did /metrics show after area ×1.3?

0.234, the 99th percentile of max-PSI over 200 no-drift windows. After area ×1.3: max PSI 0.658 on "mean area", alert true; after clean traffic, 0.187 with no alert.

Week overview, goals, project and quiz text

Status: Days 141-147 (Month 5, MLOps and ML in production) are written in full. Every number comes from code/week-21/day141_*.py to day147_*.py, each run on this box, with logs in code/week-21/out/. Shared helpers are in code/week-21/_mlops.py; the project service, tests, model card, Dockerfile and CI file are in code/week-21/project/.

Installs verified this week (pip, into the course venv): mlflow-skinny 3.17.2, fastapi 0.162.0, uvicorn 0.54.0, pydantic 2.14.1, httpx 0.28.1, onnx 1.23.2, onnxruntime 1.31.1, onnxscript 0.7.2, pytest 9.2.0. These are pinned in requirements.txt. Already present: torch 2.15.0+cpu, scikit-learn 1.9.1, scipy 1.18.1, numpy 2.5.4.

Not available, and labelled wherever it appears: - There is no Docker on the box. project/Dockerfile and project/ci/github-actions-ci.yml are written but UNTESTED: never built, never run. - MLflow's file-store backend is in "maintenance mode" in 3.17 and raises an error unless MLFLOW_ALLOW_FILE_STORE=true is set. Its sqlite backend needs SQLAlchemy, which mlflow-skinny does not include. Day 143 used the file store with that opt-out.

Compute note. The model is a 30-32-32-2 MLP on scikit-learn's bundled Wisconsin breast-cancer table (569 rows), so every script runs in seconds on one CPU thread. A GPU would change nothing here. What it changes in real production is the serving side for large models: batching and GPU memory dominate latency and cost, and Day 146's cost arithmetic would be per GPU-hour with very different throughput numbers. The load tests ran the client and server on the same machine, so they compete for CPU. The latency numbers are for localhost and include no network.
