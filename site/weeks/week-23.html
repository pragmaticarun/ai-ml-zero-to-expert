Interactive weekly quiz (12 questions)

Q1.

Day 155's saved graphs at EXTENDED and ALL contained FusedGemm. What was fused, and why did it barely change latency?

Each Gemm+Relu pair became one FusedGemm (Gemm with the activation built in). The Relu pass over the activations is tiny next to the GEMM (97% of kernel time in the profiler), so removing it saves almost nothing.

Q2.

On Day 155, what happened to batch-256 latency going from 1 to 4 to 8 intra-op threads, and what is the deployment lesson for batch 1?

676.3 → 325.1 → 313.9 µs: about 2.1x by 4 threads, then flat. At batch 1, 4 threads gave 11.3 against 15.6 µs. That gain is not worth using four cores on a phone, so default to 1-2 threads and measure.

Q3.

Why does ORT warn about saving a model optimised at ENABLE_ALL?

The ALL level can apply hardware-specific layout transforms (NCHWc) that suit this machine. Ship an unoptimised or EXTENDED graph, and let the device's runtime optimise for itself.

Q4.

On Day 156, which int8 variant was fastest at batch 256 on 1 thread, and how much faster than fp32?

Static QDQ per-tensor MinMax: 155.6 µs against 680.3 µs for fp32, about 4.4x. Dynamic int8 took 211.8 µs (3.2x).

Q5.

Every Day 156 variant scored 0.9741. What other number shows that quantization did change the model, and why does it matter?

Max |Δlogit|: 0.132 for dynamic and about 0.94 for static. Digits has wide decision margins. On a task where the top classes are close, perturbations that size would flip predictions.

Q6.

Explain the difference between dynamic and static quantization in terms of when activation scales are decided.

Dynamic measures each activation's range at run time, on every call: no calibration, small run-time cost. Static fixes activation ranges ahead of time from a calibration set: faster, but only as good as that data.

Q7.

On Day 157, why did 90% unstructured sparsity leave latency unchanged, while keeping 128 of 512 neurons made batch 256 about 9x faster?

Dense kernels multiply zeros too, so unstructured sparsity saves nothing without sparse kernels (782-807 µs at every sparsity). Structured pruning shrinks the matrices (26,122 parameters against 301,066), so batch 256 took 85 µs against 796 µs.

Q8.

Distillation lost on every seed on Day 157. Give the most likely reason, and one fair way to test distillation again.

The teacher (0.9741) has no extra knowledge: the student trains on the same clean labelled data, and with a short budget the T²-scaled KL term slows learning of the labels. A fair re-test adds teacher-labelled unlabelled data or uses a harder dataset, with α and T chosen before looking at the test set.

Q9.

Compute SmolLM2-135M's fp16 KV cache for 4,096 tokens from its config, and say how much a 9-head MHA would need.

2 × 30 layers × 3 KV heads × 64 × 2 bytes = 23,040 B per token; × 4,096 = 90 MiB (94,371,840 B). MHA with 9 KV heads would need 3x that: 270 MiB.

Q10.

On Day 158, what caused most of the +468 MiB RSS growth at a 2,048-token prefill, and how do runtimes avoid it?

The fp32 logits for every prompt position: 2,048 × 49,152 × 4 B = 384 MiB. Runtimes compute logits only for the last position, and process the prompt in chunks.

Q11.

Why was the ExecuTorch portable .pte about 100x slower than the XNNPACK one?

Portable kernels are simple reference implementations. The XNNPACK delegate runs the ops with optimised SIMD CPU kernels: 1,120.4 vs 10.7 µs.

Q12.

Why was the Day 160 Rust engine competitive at batch 1 but 6x slower than ORT at batch 256, and why was its int8 path slower than its fp32 path?

At batch 1 there is nothing to reuse, so a simple dot-product loop is close to optimal (17.0 vs ORT's 14.7 µs). At batch 256 it re-reads every weight for every row, while a blocked GEMM reuses weight tiles from cache (4,279.5 vs 683.8 µs). Its int8 loop widens each value to i32 and does not use the VNNI dot-product instructions, so int8 saved memory (308 kB) but not time (31.3 vs 17.0 µs).

Week overview, goals, project and quiz text

Status: Days 155-161 are written in full. This is Month 6's deployment week: ONNX export and ONNX Runtime tuning, int8 quantization, pruning and distillation, memory and KV-cache budgeting, shipping a model to Android, a small inference engine written in Rust, and a weekly project that holds every variant to one latency/memory/accuracy/size budget. Every number comes from code/week-23/day155_*.py to day161_*.py, each run on this box, with logs in code/week-23/out/. Shared helpers (the digits MLP, ONNX export, a median-latency bench, RSS) are in code/week-23/_dep.py. The Rust crate is code/week-23/tiny_infer/, and the Android snippets are in code/week-23/android_untested/.

Retitled from the original SYLLABUS rows. The rows for 155-158 were GPU topics (CUDA, Triton, FlashAttention, distributed training). There is no GPU here, and Week 22 already covered those ideas as UNTESTED sketches, so this week follows the deployment brief instead. The SYLLABUS rows are updated to match. The old Day 159/160 topics (ONNX Runtime, on-device Android) are now Days 155 and 159.

The model. The model is a 64-512-512-10 ReLU MLP trained on scikit-learn's bundled digits dataset (1,797 8x8 images, all offline). It has 301,066 parameters and reaches 0.9741 test accuracy on a 540-row stratified test split. This is a deliberately tiny model. It makes every experiment run in seconds, and it keeps the deployment mechanics visible. It also has a cost, stated wherever it matters: digits is easy, so int8 never changes accuracy here, and distillation does not help. Day 158 switches to the real SmolLM2-135M-Instruct config for the LLM memory arithmetic.

Not available, and labelled wherever it appears: - There is no Android SDK/NDK, Gradle, emulator or phone. Everything in android_untested/ is UNTESTED: written from the official pages, never compiled. The model files were produced and run here, on x86-64 Linux, with each runtime's Python API: ORT-format .ort files and ExecuTorch .pte files (portable and XNNPACK). That is real evidence the files are valid. It is not evidence about speed on a phone. - LiteRT: the ai-edge-litert 2.3.0 interpreter is installed and imports. Converting PyTorch to .tflite needs a separate converter package that is not installed here, so LiteRT conversion and runs are UNTESTED. - llama.cpp: there is no C++ compiler on this box and no GGUF model was downloaded, so it is UNTESTED (notes only). - No GPU: see the compute note.

Compute note. The CPU is an 8-core Xeon with AVX-512, AVX-512 VNNI, AVX-VNNI and AMX-INT8 (flags printed in the Day 156 log), with 15 GB RAM. Every latency below is from this server CPU at microsecond scale. A phone's big cores have less cache and lower clocks, and they throttle under heat, so absolute numbers will be different there. Re-measure on the device; the method is what transfers. A GPU would change Days 155-156 a little: ORT would offer the CUDA/TensorRT execution providers and fp16/int8 tensor cores, but at batch 1 on a model this small, launch overhead dominates and a GPU would probably not help. Day 158 would change a lot, since prefill on a 135M LLM is compute-bound, which suits a GPU. On phones, the equivalent accelerators are the GPU and NPU delegates/backends that LiteRT and ExecuTorch list (Vulkan, Qualcomm, MediaTek), which are UNTESTED here.

Sources (all opened and checked this week; links in docs/resources.md): the ONNX Runtime docs on graph optimisations, threading, profiling, quantization, ORT-format models, install (Android) and the Java API; the ExecuTorch "Using ExecuTorch on Android" and getting-started pages; Google's LiteRT Android page; llama.cpp's docs/android.md; and the PyTorch pruning tutorial. Explanations here are original, not copied.
