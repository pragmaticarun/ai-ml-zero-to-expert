Interactive weekly quiz (12 questions)

Q1.

In an agent loop, which component executes tool calls, and why does that matter for safety?

The harness, not the model. The model only emits text, so every capability and every risk is decided by what the harness agrees to run (validation, allow-lists, gates).

Q2.

On Day 134, SmolLM2 3-shot parsed 17/18 calls but only 6 gave the correct result. Name two logged failure patterns.

Field values used as keys ({"country": "Brindle"}, {"temperature": "Avalon"}), a runaway digit string ({"population": 8000000…}), and a bad field ("field": "city").

Q3.

Why validate arguments against a JSON Schema before executing a tool?

Side effects can't be undone after execution, and a precise validation error ("$.field: 'area' not in [...]") is an observation the model can act on.

Q4.

On Day 135, why did ReAct (0/24) score below direct answering (3/24) for SmolLM2?

Each extra step was another chance to fail: it made repeated invalid calls (95 tool errors, 18 step-limit hits) and even garbled the final step after correct lookups (answered 45000 for gold 165000).

Q5.

At p=0.3 tool failure, give the success rates of plan-no-retry, plan-with-2-retries and ReAct (Day 136).

0.401, 0.924 and 0.995.

Q6.

Why did BM25 top-1 memory score 0.00 on updated facts while the key-value store scored 1.00?

The old and new statements are equally similar to the question, so a single retrieved snippet was often the stale one. The KV store overwrites on update.

Q7.

Which two sandbox probes on Day 137 succeeded when they should have failed, and what does that imply?

Reading /etc/hostname and writing to /tmp outside the working directory. The rlimit sandbox bounds resources but does not isolate the filesystem, so it is not a security boundary; real isolation needs containers or microVMs.

Q8.

Why did the sleep probe need the wall-clock timeout rather than the CPU rlimit?

Sleeping uses no CPU time, so the 2 s CPU limit never fires. The 5 s wall-clock timeout killed it at 5.01 s.

Q9.

Define pass@k and pass^k, and give the noisy policy's values for k=8 on Day 138.

pass@k: solved in at least one of k trials. pass^k: solved in all k. Noisy policy: pass@8 1.000, pass^8 0.458.

Q10.

Why is a bootstrap CI of [0.000, 0.000] for 0/24 misleading?

When all outcomes are identical, every resample is too, so the interval collapses. Zero successes in 24 does not prove a zero rate; the rule of three gives a rough upper bound of 3/n.

Q11.

On Day 139 / Day 140, why did success stay unchanged under injection, and which defence removed the emails?

The injected email was an extra side effect, and the answer was still right, so outcome metrics missed it (22/24 emails queued on Day 139 at 24/24 success; 1.000 emails/run on Day 140). The per-task allow-list and the confirmation gate both brought emails to 0.

Q12.

Constrained decoding on Day 139 gave 24/24 valid outputs but only 18/24 fully correct. Explain.

Constraining guarantees syntax and schema validity, but it still chose the wrong valid field for 6 requests (field right 18/24). That is a semantic error no grammar can fix.

Week overview, goals, project and quiz text

Status: Days 134-140 (Month 5, LLM agents and tool use, built from scratch) are written in full. Every number comes from code/week-20/day134_*.py to day140_*.py, each run on this box (CPU only, 4 threads, offline Hugging Face cache), with logs in code/week-20/out/. Shared helpers: code/week-20/_agent.py (schema validator, tools, agent loop, task suite) and code/week-20/_sandbox.py (subprocess code runner). The MLOps topics that used to sit in Week 20 move to Week 21 and later.

Honesty note on the policy. The only local language model used is SmolLM2-135M-Instruct (already in the course cache since Week 15). It is far too small to act as an agent. Day 134 measured 0/18 correct tool calls zero-shot and 6/18 with three examples; Day 135 measured 0/24 on the ReAct task suite. So from Day 136 on, the "policy" (the part that chooses the next action) is usually a scripted or mock policy, and every place that happens is labelled. Those days test the harness: the loop, validation, retries, memory, the sandbox, evaluation and the defences. They do not show what a real LLM would do.

Compute note. The agent machinery is CPU-trivial: Day 140's 12 conditions × 192 runs took 0.0 s of wall time with scripted policies. The cost is all in the model. SmolLM2 took 0.59-0.99 s per tool call request on Day 134 and 3.96 s per ReAct task on Day 135. A GPU would make a 7B-70B instruction-tuned model practical. Models of that size are trained for function calling, so the Day 134-135 rows would change, and the injection tests on Day 139 would become meaningful: a model that follows instructions well also tends to follow injected ones. None of that is run here, so no number in this file describes a large model.

Sources (opened and checked): Model Context Protocol architecture overview, https://modelcontextprotocol.io/docs/learn/architecture; ReAct paper, https://arxiv.org/abs/2210.03629.
